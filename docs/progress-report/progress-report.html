1. System Overview

The system is a web-based self-service ordering kiosk with integrated real-time stock inventory and transaction management for Zak's Sizzling Hub, a sizzling-plate restaurant. Customers order on an in-store touchscreen kiosk (a Raspberry Pi with a 1024 × 600 display) or on their own phones by scanning a QR code. They browse the menu by category, search or filter by price, add dishes with special instructions, choose dine in or take out, and pay at the counter (online payment through QR Ph is implemented but not yet live). Each order receives a unique order number and an estimated preparation time, and on the in-store kiosk the receipt is also printed on a thermal printer.

Staff use a back office on a separate address to confirm counter payments, follow orders on a kitchen display that updates in real time, adjust stock with a recorded reason, and look up products by barcode. When an order is paid the system deducts stock automatically, either as units or as raw materials according to each dish's recipe, and every open kiosk updates its sold-out items without refreshing. The Administrator additionally manages products, prices, costs and photos, imports products in bulk from CSV or Excel files, views sales analytics with CSV, Excel and PDF export, manages user accounts and roles, and prints the kiosk QR code.

A background worker checks stock levels every hour, sends low-stock e-mail alerts when e-mail is configured, and backs up the database every night to off-site cloud storage. The system is deployed on Railway as separate customer and staff web addresses, an API service, a worker and a managed PostgreSQL database. This report describes only what is present in the source code; every status in Section 4 cites the files that implement it.

5. Completed Features

The completed work covers the full ordering cycle and the back-office tools around it. The figures are low-fidelity wireframes drawn from the current code (docs/diagrams/); each names the files it is based on.

5.1 Customer ordering

The kiosk opens on a welcome screen and asks once whether the customer will dine in or take out. The menu shows one category at a time, with a category rail, keyword search and price-range chips; sold-out dishes are dimmed and update live. Customers add dishes directly or through an item sheet with quantity, quick instruction options and a note. Checkout shows the order, an estimated preparation time based on the kitchen queue, and the payment choice (Pay at counter, or QR Ph once online payment is set up); placing the order returns a receipt with a unique order number. Inactivity triggers a warning and then resets the kiosk for the next customer.

5.2 Counter payment and kitchen

The cashier finds the order by its number in Orders awaiting payment and confirms it. Confirmation marks the order paid, deducts the stock and creates kitchen tasks in a single database transaction; if any item has run out, nothing changes and the cashier is told before money is taken. Unpaid orders can be cancelled. Paid orders appear immediately on the kitchen display, where each dish moves from Pending to In progress to Completed, with dine-in and take-out orders distinguished.

5.3 Inventory

Stock is tracked per product (units) or per raw material for dishes made from a recipe; the kiosk shows how many servings the raw materials still allow. Each item has a minimum level, and items at or below it appear on the dashboard and stock pages and are queued for an e-mail alert. Every manual change requires a reason and is logged with the person, the time and the before and after quantities. Products can also be found by scanning or typing their barcode.

5.4 Products, analytics, users and operations

The Administrator creates and edits products with validation, photos, preparation times and recipes, and imports products in bulk from CSV or Excel after a row-by-row check. Analytics show daily, weekly and monthly sales, top-selling products, profitability and inventory movement, each exportable as CSV, Excel or PDF. User accounts can be created, assigned a role, suspended and reactivated. The Administrator also prints a QR code that opens the kiosk on customers' phones. In operation, the worker backs up the database every night to off-site storage, and separate web addresses keep staff pages off the customer link.

5.5 Security and quality

Passwords are hashed with bcrypt, staff sessions use short-lived tokens, all input is validated, responses carry security headers, only the kiosk and admin addresses may call the API, payment webhooks are verified by signature, and repeated sign-in, order and payment attempts are rate limited. The API and worker are covered by automated unit, integration and security tests (Section 8).

7. Known Issues and Limitations

7.1 Functional

  1. Order status after cooking. The database defines the statuses preparing, ready and completed, but the code never sets them; an order remains "confirmed" after the kitchen finishes, and the customer is not notified that it is ready (apps/api/src/modules/kitchen/service.ts).
  2. Changing an order. When stock runs out at confirmation, the cashier is told to change the order with the customer, but no screen edits an existing order. The API provides routes to change or remove order items that the web application does not use; in practice the order is cancelled and placed again.
  3. No live refresh of the payment queue. Orders awaiting payment loads when opened and after each action; a newly placed order appears only after the page is reloaded.
  4. Data without an input screen. Categories, and each dish's ingredients, allergens and nutrition (shown on the kiosk), can only be changed directly in the database.
  5. Online payment gaps. A customer who cancels on PayMongo's page returns to an empty checkout page, and a payment not confirmed within five checks is shown with the pay-at-counter wording. Neither case occurs in production while online payment is disabled.
  6. Receipt content. The print service prints the order number, date, items and total, and always ends with "Please pay at the counter". It does not yet print the restaurant name or the order type, and receipts after an online payment are not printed.
  7. Account passwords. Users cannot change their own password, and temporary passwords given to new users are not required to be changed.
  8. Low-stock e-mail in production. The alerts are queued, but the production worker has no e-mail key, so no e-mail is sent there.

7.2 Security and maintenance

  1. Hosting provider incident. On 21 October 2026 Railway disclosed unauthorised access to customer environment variables and advised rotating every secret. The three token secrets have been replaced; the database password and the backup-storage and e-mail keys remain to be rotated, and Railway paused deployments during its investigation.
  2. Dependency advisories. npm audit reports 18 advisories in production dependencies (3 critical, 9 high, 6 moderate), all with fixes available. The critical advisory in Next.js concerns next/og, which the system does not use; the others should still be resolved by upgrading.
  3. Browser token storage. Staff access tokens are kept in browser storage, which a cross-site scripting flaw could expose; the impact is limited by the 15-minute token lifetime and the httpOnly refresh cookie.
  4. Print service exposure. The print service on the Raspberry Pi accepts requests from any web page, but listens only on the Pi itself.
  5. Lint findings. ESLint reports 11 errors and 6 warnings in the web application (mostly state updates inside effects); type-checking reports none.
  6. No automated tests for the web interface. The screens were checked manually in a browser.
